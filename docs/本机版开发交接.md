## 当前实施方案

- **本机优先。** 新工作台默认选择本机目录。扩展把业务数据写入所选目录下的 `URLPut-data-v1`。实际实现使用 JSON 保存站点、批次、回执、队列、分段结果和核验台账。IndexedDB 当前保存目录授权句柄。导入、历史查看和导出不依赖 URLPut 业务 API。网站分析和核验由客户端访问目标站点。旧版服务工作空间供访问和迁移原历史。
- **串行运行。** 同一浏览器配置的窗口共用一个执行锁。HTTP 可访问性检查用 HEAD，网站分析和公开评论核验用只读 GET。一次主动请求处理一个 URL，发起间隔至少 2 秒，超时 15 秒，遇到 429 处理 Retry-After。读取 HTML 时流式解析并限制为 16 MiB。单条失败后保留原因并继续。导入批次的检查和分析有本机检查点，可在重开后手动继续。
- **结果以证据为准。** 平台明确接收并等待管理员审核时，在来源行手动登记回执，显示「提交成功 / 待审核」。定位到公开评论内的目标链接后才计为有效外链。回访缺少证据进入待核实，404/410 可标记公开页失效，暂时访问失败保留上次核验结论并记录失败原因。
- **范围基准。** 先读 `docs/architecture/local-first-results.md` 和 `docs/planning/implementation-plan.md`。架构文档含目标状态，例如 IndexedDB 索引和待写回队列。下表记录已落地能力，原计划中的日期是旧方案估算。

## 下一窗口施工顺序

1. **先验收真实安装。** 用允许解包扩展和目录授权的 Chrome，在业务 API 和数据库关闭时跑通选择目录、导入、刷新、关闭并重开浏览器、重新授权、恢复队列和 CSV 导出。确认业务 API 零请求。云端 Chromium 的管理策略限制解包安装和原生目录授权，当前真实测试停在等待扩展 service worker 启动。
2. **批量回访中断续跑已实现。** 筛选结果在启动时保存为本机队列。重开工作台后，在对应推广站点的已核验外链台账中点「继续批量回访」。结果与检查点在同一文件提交，已保存的条目会跳过。回访继续复用全局执行锁和限速，网站访问失败保留上次结果和本次原因。
3. **动态线索和跨批次浏览已实现。** 网站分析和回访从公开静态 HTML 记录可见登录提示及已知动态评论组件标记。仅在评论表单中发现的必填字段进入结果，缺乏证据的字段保留未知。工作台按当前推广站点浏览网站分析，支持批次和结果筛选并导出；已核验外链台账仍按站点汇总，待审核回执保留在来源批次。动态渲染内容需人工确认。
4. **本机目录备份和恢复已接通。** 见下方操作步骤。真实 Chrome 中的目录移动和权限撤销仍待验收。已按单批 5,000 条导入上限完成受控长队列测量，见下方。跨批次分析按本机实际存在的结果分段读取，浏览器回归包含 20 个各 5,000 行且未生成分析结果的历史批次，结果页只打开有数据的两个分段。受控样例已覆盖跨结果分段的 35 条队列、HTTP 429、按 Retry-After 限流、15 秒超时后继续，以及 16 MiB HTML 响应上限。浏览器回归在第 2 条请求期间关闭整个 Chromium 进程，以同一配置目录重启并模拟重新授权，从第 2 条续跑，已保存的第 1 条不再访问。该回归使用真实 Chromium 持久配置、IndexedDB 和 OPFS，模拟扩展 API 与目录授权。
5. **手动投稿已接通逐条批准和占位。** 在来源批次打开「逐条批准手动投稿」，选择候选并保存审核后的文案。扩展先把批准和占位写入本机目录。用户点「开始单次手动投稿」时，扩展持久化开始状态后只打开一次平台入口，由用户在平台手动登录、核对并提交。刷新、断线和打开入口失败后均以核对平台状态为准。旧版占位若无开始状态，按未知处理。相同推广站点和规范化候选网址跨批次防重，历史待审核回执也纳入检查。登记回执时同样检查该网址是否已有回执；若已有投稿占位，只能在占位对应的批次和来源行登记。提交后沿用待审核回执及只读公开核验。受控样站回归已覆盖一次手动提交、平台收到请求后连接断开、只读查回执、关联来源行，以及公开后核验与导出。自动投稿、账号流程和真实授权站点端到端验收仍待交付。

## 目录备份、恢复和换绑

- 备份：结束正在运行的只读任务，点「备份数据目录」，选一个尚无 URLPut 数据的文件夹。应用逐个复制 `URLPut-data-v1` 下的 JSON，数据文件全部写完后再写工作空间文件。批次、回执、台账、结果及队列检查点随目录复制。
- 恢复：点「选择备份来源」，选包含 `URLPut-data-v1` 的上级文件夹。再点「选择恢复目标并恢复」，选择另一个空目标。复制成功后工作台切换到恢复目录。此后可手动继续尚未完成的只读检查和回访。
- 换绑：目录被移动时，点「重新选择数据目录」，选择移动后的上级文件夹。重新绑定要求所选位置有现成数据；要新建工作区，使用「初始化空数据目录」。浏览器回归通过复制到测试目录并移除旧位置，验证了错误路径被拒绝、原结果可重新读回、后续数据写入新位置。目录位置仍有效但权限丢失时，点「重新授权原目录」。切回已打开的工作台时会重新检查权限，失效后暂停本机工作台，重新授权成功即可读回原数据。使用系统文件管理器手动复制时，先关闭所有 URLPut 工作台，再复制完整的 `URLPut-data-v1`。
- 复制遇到空间不足或页面关闭时，使用另一个空目标重试。旧数据和已完成的备份可以继续使用。浏览器保存的目录授权和扩展偏好需要在恢复环境中重新配置。

## 5,000 条队列测量

```sh
URLPUT_LONG_QUEUE=1 URLPUT_WEB_SMOKE=1 CHROMIUM_PATH=/usr/bin/chromium npm run test:extension
```

以 CSV 导入 5,000 条，在 Chromium 持久配置中运行。首个站点返回 429，后续同源条目直接记录限流，另两个站点分别超时和成功。首轮仅发出 3 个受控请求。此次运行耗时 35.5 秒，含一次 15 秒超时。应用共读取结果分段 160 次，写入 5,000 次，提交的 JSON 累计 16.8 MiB。Chromium 页面 JavaScript 堆从约 21 MiB 起步，写入时采样峰值约 61 MiB。测试夹具模拟冷却结束后，单条恢复耗时约 2.1 秒。

这组数据衡量本机结果持久化和限流队列。实际逐条联网耗时、浏览器进程总内存和用户目录所在磁盘的吞吐量取决于使用环境。

## 生成 Chrome 内测包

在仓库根目录执行 `npm run package:chrome`。该命令重新构建 Chrome Manifest V3 扩展，并在 `apps/extension/.output/` 生成 `URLPut-WXT-0.1.0-chrome.zip`。交接时可在副本文件名中附上 Git 提交号。解压后，从 `chrome://extensions` 加载包含 `manifest.json` 的目录。

回归开始时确认 4310 端口关闭。在本机导入、目录恢复、回执和重启续跑用例期间，Fastify 和 PGlite 均未启动，并记录浏览器配置下所有测试窗口发出的业务 API 请求。通过零请求断言后才启动旧版服务，验证历史迁移。

也可直接对解压目录跑模拟扩展 API 的 Chromium 回归。将路径替换为包含 `manifest.json` 的目录：

```sh
URLPUT_EXTENSION_DIR=/path/to/unpacked URLPUT_WEB_SMOKE=1 CHROMIUM_PATH=/usr/bin/chromium npm run test:extension
```
