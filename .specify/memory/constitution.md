# URLPut 项目章程

## 核心原则

### 一、先思考，再编码

修改前必须明确用户目标、现有实现、兼容性和验收标准。
影响范围或验收的关键歧义必须先澄清，次要假设应记录在计划中。

### 二、简单优先

必须选择满足产品需求且易于维护的方案，优先复用现有组件、
数据格式和依赖。引入新抽象或服务须在计划中说明必要性。

### 三、精准修改

变更必须围绕已批准范围。涉及历史数据、对外接口或跨模块改动时，
须说明影响范围、兼容措施和恢复路径。

### 四、目标导向

各阶段须有可检查的产出。交付须按实际运行证据核对成功标准，
并记录所有未验收或受阻的场景。

### 五、界面品质优先

界面变更须沿用现有设计体系，覆盖交互反馈、加载、空、错误和禁用状态。
有可用浏览器时，须实际检查渲染、关键操作与受影响窗口尺寸。

## 产品与数据边界

- 本机版核心流程须在业务服务关闭时可用。数据由用户选定目录管理。
- 只读队列须遵守串行、超时和限流约定，并可从已保存位置续跑。
- 外部投稿须逐条人工批准并由用户在平台提交。正式验收须获得站点授权。
- 待审核回执和公开核验结论须分别记录，核验结果须关联可追溯的证据。

## 开发与验证

- 小改动直接验证，中型变更记录范围和步骤，大型变更采用 Spec Kit。
- 按影响范围选择类型检查、测试、构建和真实浏览器回归。
  模拟扩展测试与真实 Chrome 验收分别记录。
- 缺陷修复须考虑中断、重试、并发和已有数据。敏感凭证须留在授权范围内。

## 治理

章程修订须说明理由、受影响范围和迁移安排，并获项目维护者确认。
原则的不兼容变更升主版本，新增原则或规则升次版本，澄清升修订版本。
计划及交付复核须核对章程，说明例外及其影响。
完成 Specify 和 Plan 后，须取得用户明确确认才进入 Tasks、Implement 或 Converge。
