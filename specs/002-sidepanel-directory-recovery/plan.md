## 摘要

先固定原型和撤权证据，再将目录管理集中到设置。把建批编辑状态与目录可用状态解耦，按工作空间身份恢复或校验草稿。复用现有文件操作，并核对失权时保存和续跑的一致性。

## 技术背景

Node.js 24、TypeScript、React、WXT 和 Chrome MV3。JSON 保持在 `URLPut-data-v1`，授权句柄使用 IndexedDB，同配置的写入和队列沿用 Web Locks。目标环境为 Windows 桌面 Chrome 的工具栏侧栏，重点验证 320 px 与 392 px，目录状态更新只读工作空间和必要元数据，避免遍历历史。保留全页入口和旧版服务迁移入口。

## 章程检查

- 设计前复核了现有侧栏挂载、授权和文件写入路径。规格包含用户目标、兼容性及可测结果。
- 设计后复核采用现有组件和存储格式，以设置导航、草稿生命周期和必要的写入恢复为改动边界。无需新服务和新依赖。
- 兼容路径包括旧目录读回、重复操作、备份中断和工作空间切换。关闭业务 API 和数据库后，验证 01–02 本机目录流程的业务 API 请求数为 0。随后由开发方启动本地业务 API，用测试数据验证旧版服务工作空间可访问、历史可迁移且重复迁移不产生重复记录，单独保留请求与迁移证据。用户也可独立复验。
- 原型、模拟扩展和桌面 Chrome 分别记录。键盘、状态反馈和两个目标宽度均进入验收。暂无章程例外。
- 已获用户确认。Tasks、Implement 和验收按此范围执行。

## 实施顺序

1. 固定两个宽度的原型对照表和基线撤权截图，包括默认展开态、字段、启动条件及往返焦点。标注「新建批次仅剩目录操作」。
2. 实现设置入口和目录状态。保留六项导航及当前能力对应的可用状态。原生授权从按钮事件发起。
3. 保持草稿在面板会话中，区分无绑定、失权、已有目录不可读取与可用。使用工作空间 ID 判断恢复与切换，切换前后隔离异步结果，清理无效引用。
4. 核对写入链路。存在半途失败时沿用稳定记录标识，按待确认操作对账后重试。绑定提交前验证目标。管理操作遵守已有锁顺序，确保运行时能辨识冲突并重试。
5. 验证后归档运行证据。若目标 Chrome 暂不可用，记录原生权限验收受阻和具体原因。

## 兼容与恢复

旧 JSON 无迁移。目录最近写入以当前面板会话已确认的写入时间为准，未记录显示「暂无记录」。旧目录历史时间保持原样。切换失败保留原绑定，部分复制用另一个空目标重试。切回原目录可继续已保存队列，已有回执和来源关联可读。

本地 API 验收在零请求用例完成后执行，使用 `npm run dev:api -- --local`。
