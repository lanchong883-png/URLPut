# 分阶段验收指南

用 Node.js 24 运行 `npm ci`、`npm run check`、`npm test`、`npm run package:chrome`。在 320 px 和 392 px 使用 Windows Chrome 工具栏打开解包扩展，记录构建提交、Chrome 版本、截图、请求、CSV 与目录证据。用模拟扩展 API 回归做补充，并标注其环境。

| 验收段 | 操作 |
| --- | --- |
| 03–05 | 以两站和两清单验收导入、过滤、回焦、六组合预览、重复点击及拒绝授权。另用 100 × 1,000 夹具检查分段和分页。关闭侧栏后重开检查同批处理。 |
| 06–08 | 两窗口运行检查、分析和回访，记录峰值、间隔、超时、429 和退避。测试暂停、中断、停止、重启及队列去重。对照各结果归属、失败反馈和导出前九列。 |
| 09–10 | 受控模型和站点验证模板分支、草稿复用、额度、平台防重、网络中断及回执。正式站点获授权后，由用户逐条在站点提交，核验公开证据与 CSV。 |
| 每阶段 | 先关闭业务 API 和数据库，记录业务请求数为 0。再用测试数据运行 `npm run dev:api -- --local`，验证旧工作空间访问和重复迁移。 |

## 当前验证记录

- 基线为 `0482741` 上的 01–02 与 03–10 本地工作树。Node.js 24 通过类型检查和 20 项现有单元、接口测试。
- Chromium 156 受控浏览器验证了本机清单导入、重复原始行保留、待检查转活跃、带来源日期的 DR 0、返回建批焦点、两站共享快照、暂停和继续、模板版本与人工占位。先执行服务停用零请求断言，再启动测试 API 复测旧工作空间和两次迁移。另直接运行本地 CLI，健康与工作空间接口均为 200。
- Linux Chrome for Testing 159 实际加载扩展，验证真实 Service Worker 与 offscreen 文档在发起页关闭后完成一条测试记录落盘。该用例使用 OPFS 句柄夹具，结果用于证明生命周期。两个目标宽度验证 100 站 × 1,000 条的计数、分页和每站上限，尚未执行 100,000 条网络请求。
- 实际安装扩展的受控模型用例已验证使用启动快照中的模型生成草稿、保存与重复使用。另以两条已有尝试验证跨 URL 的人工平台占位检查和滚动 24 小时额度解除。用例不产生站外投稿。
- 待验收的环境包括 Windows 工具栏的真实侧栏和原生目录选择/撤权，以及有授权站点的用户手动提交、公开后的回执闭环。执行范围见 [Tasks](tasks.md)。

### 06–08 后续回归

- 全批与单站的候选、已处理和待处理由已提交的分析分段与完成记录计算。已接收和有效分别来自回执与公开核验台账。任务按状态筛选时仍可按名称和编号定位。
- 相同本机目录中，推广站点与规范化候选 URL 相同的多站分析可共享成功结果，保留原始完成时间与来源批次。失败结果仍可重试。
- 跨批待确认可从投稿占位或准备草稿的失败原因直接打开原批次与候选。已登记回执的记录在原来源任务保留审核和公开核验状态。
- 多站 CSV 可按全批、单站与结果状态导出，保留原九列顺序，追加批次、预期与实际目标、核验证据、回执及分析来源。

最终内测包的 Chromium 回归通过，覆盖进度、状态筛选、导出前九列、跨批分析复用（重叠批次网络请求数维持为 2）、跳回原候选，以及关闭和启用业务服务两条路径。Linux Chrome for Testing 加测中断和停止状态跨重启保留、人工续跑，以及受控模型 HTTP 503 原因落盘和定位。目标 Windows 侧栏原生权限和授权站点端到端验收待完成。

### 09–10 回执闭环

在受控多站场景中，批准后尚未开始时登记回执会被拒绝。开始后由测试操作者在模拟目标页完成一次提交，目标收到 POST 后主动断开响应。重新打开页面只读查到回执，并从原批次登记。错误预期目标被拒绝，随后按批次快照网址成功关联公开评论。导出同时含回执编号、定位片段和有效外链状态。整个模拟场景的提交次数为 1，业务 API 请求数为 0。另以临时数据目录启动本地业务 API，健康与工作空间接口均返回 200。

### 100,000 组合调度

Chromium 156 持久配置与 OPFS 受控夹具中，100 站 × 1,000 条候选生成约 319 KB 的共享快照与 100 个站点任务，队列只写入一次。从点击启动到任务页约 0.9 秒。构造已完成一站、另一站保有首条检查点、队列未写全且缺少一个站点索引的中断状态。完整重启后修复索引、保留已有任务编号与行检查点、跳过完成站点，恢复 99 个唯一任务，队列一次写入。任务页显示已处理 1,001 条，单站结果从第 200 条翻页到第 201 条。

本规模测试阻止全部外部请求，验证的是持久化调度和分页。Linux Chrome for Testing 另以小样本测试真实 Service Worker、关闭发起页继续处理、重启后保留停止状态和手动继续。外部 100,000 条请求吞吐和 Windows 原生权限未在本环境实测。

投稿候选可在批准前跳过，决定以来源批次、站点和行号保存。在 Linux Chrome for Testing 实装扩展中，受控模型失败的候选跳过后从待确认清单消失，CSV 保留「已跳过投稿」和时间，投稿尝试文件没有写入。重启浏览器并重新打开原候选，跳过状态仍在。

待确认清单在草稿失败原因、批准占位、开始尝试、跳过及回执成功落盘后自动刷新。Linux Chrome for Testing 的两个扩展窗口同时打开待确认，跳过后两个窗口均自动移除该候选。刷新不轮询业务 API。

当原尝试已开始且回执待核对时，从待确认清单打开原批次，再点「打开原平台核对回执」。受控站点故意在接收表单后断开连接，回归重载扩展页面并用该入口查询。核对请求为 GET，模拟平台只收到一次 POST，仍由用户在来源批次登记回执。

从已开始的原尝试点「登记此条回执」会在同一批次展开登记表、预填原候选序号，并把焦点移到回执编号。提交时间仍由用户根据实际记录填写。受控回归在重载后从待确认打开原尝试，经原平台查回执，再用快捷入口补登和完成只读核验。
